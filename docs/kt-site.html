Musterbox HRMS

A multi-tenant HR, payroll and workforce platform for Indian businesses. This is the orientation map: how the Angular client is put together, how the five user types differ, and what every screen has in common.

01The product

One login covers the whole employee lifecycle. The product is broad rather than deep — roughly six hundred screens spanning hiring, attendance, payroll, statutory reporting and exit.

Tenancy

One deployment serves many companies. A company may own child companies, and every list request carries a companyMasterID — that field is the tenant boundary.

Who uses it

All five are created through the same companycontact/v1 endpoints. The admin field in the payload is the only thing that separates them.

02Architecture

An Angular 10 single-page app with hash routing, talking to a separate Node REST service. All HTTP goes through one method on one service; all URLs come from one catalogue.

Routing, in three layers

// 1 · root — app.routing.ts
RouterModule.forRoot(routes, { useHash: true })   // all URLs carry a #

// 2 · views.routing.ts — THREE tables, chosen at module import time
let routes = [ /* A · with AuthGuard */ ];
if (localStorage.getItem('token'))  routes = [ /* B */ ];
if (!environment.isAuthGuardActive) routes = [ /* C · NO AuthGuard */ ];

// 3 · feature routes — one lazy module per menu item
/#/app/masters      → MastersModule      → vendor_master → VendorMasterModule
/#/app/attendances  → AttendancesModule  → …

isAuthGuardActive is false in production, so table C wins and AuthGuard is never attached in prod builds. The tables are also evaluated once, at import — logging in or out does not re-evaluate them, which is why several flows call window.location.reload().

Response envelope

The HTTP status is almost always 200. The status that matters lives in the body, so components branch on res.status, never on HTTP codes.

{ "status": 200, "message": "Data fetched successfully", "data": [ … ] }
Body statusMeaningWhat the app does
200Successres.data consumed
400Validation or business errorres.message as an error toast
403Token invalid or expiredSession-timeout modal → clear storage → appLoginUrl
500Server errorGeneric error toast

03Roles & access

This is the part newcomers get wrong. There are three independent access-control layers, with different data, different screens and different APIs.

Layer 1
User type

One number, 0–4, in localStorage.usertype. Decides which menu tree is built and where you land after login.

Layer 2
Role & permission

A form × operation matrix. Decides which menu items exist and which Add / Edit / View / Delete buttons render. Applies to user types 0 and 1 only.

Layer 3
Authorization

Approval routing. Decides whose leave, expense, overtime and gate-pass requests land in your inbox. Unrelated to Layer 2.

What each user type sees

How a permission reaches a button

The menu: key is a magic string. IMenuItem.menu must exactly equal the backend's formName. There is no compile-time check and no runtime warning — a mismatch just makes the menu item vanish for permissioned users while it still shows for admins. This is the single most common “my new screen doesn't appear” cause.

A failed permission call looks like full access. The sidebar's error handler deliberately keeps the unfiltered menu so the user isn't stranded with no navigation. “I can see everything” can mean the permission API is down, not that the user is an admin.

Layer 3 — approval chains

Authorization is configured separately, under Org → Authorization. It maps a request type and an employee slice (branch, department, designation) to an approver, and supports multi-level sign-off.

06Backend API

The backend is a separate repository. What follows is the contract as this frontend consumes it — derived from ConstantService and ApiService.

URL convention

<baseUrl><resource>/v<n>/<action>[/<id>]

POST   companymaster/v1/add
POST   companymaster/v1/getalldata        ← POST is used for reads: filters go in the body
GET    companymaster/v1/getbyid/42
POST   companymaster/v1/updatebyid
POST   companymaster/v1/deletebyid
POST   companymaster/v1/statuschange      ← 'statuschanges' also exists, per resource
GET    companymaster/v2/getalldata        ← v1/v2/v3 coexist; check the constant

Never hard-code a URL in a component. Add a constant to ConstantService and reference it. Naming there is inconsistent by era — older resources use getalldata, newer ones listRoleMaster — so read the constant rather than guessing.

Authentication

POST {apiUrl}auth/v1/login
→ { status: 200, data: {
      token, usermasterid, companyMasterID,
      admin,           // the user type, 0–4
      childcompany, resetpassword, permission } }

// every subsequent request
Authorization: Bearer <token>      // attached by ApiService.headerInit()

The JWT payload is nested: jwtDecode(token).token.userType. There is no refresh-token flow — an expired token produces status: 403, which triggers the session-timeout modal.

List request shape

{
  page: 1, limit: 10,
  startdate: '', enddate: '', searchQuery: '',
  companyMasterID: localStorage.getItem('company_id')   // ← the tenant boundary
}

Bulk-import pipeline

Masters that accept Excel upload expose a five-step family. Demo templates are also checked into src/assets/*.xlsx.

generateDemoExcel → (user fills it) → validateExcel → revalidate<Entity> → addValidate<Entity> → uploadexcel

07Adding a screen

The eight steps, in order. The full worked example — a fictional Vendor Master, with complete component code — is in docs/08-adding-a-screen.md.

  1. Register the form in the backend catalogue

    Super Admin → Form Master, with formName = "VendorMaster" and the operations you plan to gate on. Not optional — skip it and the menu item never renders for a normal user.

  2. Add the endpoints to ConstantService

    Under a new // vendormaster comment header, following the existing naming.

  3. Create the folder

    views/app/masters/vendor_master/ with list-, add-, edit- components plus a module and routing module. Mirror a neighbouring master exactly.

  4. Write the feature routing module

    '' → list, add_vendor → add, edit_vendor → edit.

  5. Write the feature module

    Copy the import list from a neighbour: NgxDatatable, NgSelect, PagesContainers, Pagination, Modal, SimpleNotifications, NgxUiLoader, Translate.

  6. Lazy-load it from the parent

    Add a loadChildren entry to masters.routing.ts.

  7. Add both menu entries

    constants/menu.ts and constants/headerItems.ts. The menu: key must exactly equal the backend formName.

  8. Implement list, then add/edit

    List: ngx-datatable + checkpermission() + server-side paging. Form: template-driven ngForm + audit fields + companyMasterID.

08Gotchas

The traps that each cost a new developer about a day.

Routing  Three route tables, chosen at import time

views.routing.ts declares let routes then reassigns it twice, based on whether a token exists and on isAuthGuardActive. Evaluated once, when the module is first imported — logging in or out does not re-evaluate it. In production isAuthGuardActive is false, so the unguarded table always wins.

Security  AuthGuard barely guards

canActivateChild only checks that a token string exists in localStorage; the role check is commented out. Real enforcement is the backend returning 403. Treat the frontend as presentation-layer gating, never as a security boundary.

Build  npm run build:stage is broken

It calls ng build --configuration=staging, but angular.json has no staging configuration and there is no environment.staging.ts. Add both, or use build:prod.

Build  The Node flags are mandatory

Without --openssl-legacy-provider the build dies with ERR_OSSL_EVP_UNSUPPORTED; without --max_old_space_size=8096 it runs out of heap. Both are already in the npm scripts — don't call ng directly.

Menus  The menu: key is an unchecked magic string

It must equal the backend formName exactly. No compile-time check, no warning. The item simply disappears for permissioned users while still showing for admins.

Permissions  A failed permission call looks like full access

The sidebar keeps the unfiltered menu when finalcheckpermission errors, so the user isn't stranded. Seeing everything can mean the API is down.

Legacy  Template leftovers that mislead

The project started from the Vien Angular admin template, and several artefacts survive unused:

  • shared/auth.roles.ts — enum UserRole { Editor, Admin } is not the real role model; the real one is the numeric usertype 0–4
  • shared/auth.service.ts — Firebase auth; real auth is the backend JWT
  • environment.firebase — points at the template author's demo project
  • data/api.service.ts, data/charts.ts — template demo data, unrelated to services/api.service.ts
  • ApiService.callApi static overload and ChatService.getMsg() both throw Method not implemented.

Naming  Spelling you must not casually “fix”

These are load-bearing — grep before renaming: route reuqestInbox, constants UPDATEOMPANYDATA and DELETEOMPANYDATA, backend path citymaster/v1/getbgetCityBystateIdyid/, resources erpIngegration and resigantionReason, folder asignassettoemp, and both statuschange and statuschanges.

Repo  The working tree is not clean

Branch local carries a large set of modified files and some deletions — notably src/app/company-structure/* is deleted while AppModule still declares CompanyStructureComponent. Run git status before assuming a file is missing. Two lockfiles are also committed; pick one package manager and stay with it.
